# 공유 기록 동기화 변경 및 검증 (2026-10-29)

## 변경 범위

- `tennis_shared_state` id=1의 기존 8개 공유 필드만 대상으로 한다. 대진표 생성,
  점수 증가/타이브레이크, 경기 결과/통계 계산과 기존 세션 저장 코드는 변경하지 않았다.
- 저장 확인 응답의 오류와 반환 레코드를 검증한다. 성공 응답 전에는 기준 상태를
  갱신하지 않으며, 응답을 기다리는 동안 추가한 입력도 별도 저장 대기로 남긴다.
- 800ms 디바운스, 최대 한 개의 진행 중 작업, 15초 요청 제한, 실패 후 1~30초
  재시도 대기 및 5초 주기 재확인을 적용한다. 온라인 복귀 및 수동 재시도도 지원한다.
- 미저장 기록과 저장 기준을 `tennis_shared_pending_v1`에 보관한다. 새로고침 후에도
  서버 기록과 비교한다. localStorage 실패는 화면에 표시하고 JSON 백업을 제공한다.
- 서버가 변경되고 내 미저장 기록도 있으면 자동 갱신/저장을 중단한다. 사용자가 두
  기록을 비교하여 서버 적용 또는 내 기록 전체 저장을 명시적으로 선택한다.
  선택 전 양쪽 기록을 `tennis_shared_conflict_backup_v1`에 백업하며, 실패 시 중단한다.
  이 키에는 마지막 충돌 선택의 백업이 남는다. 장기 보관은 JSON 내려받기를 사용한다.
- 한 UPDATE의 WHERE에 기존 8개 필드 전체를 조건으로 넣는 compare-and-swap을
  사용한다. 사전 조회만으로 안전하다고 판단하지 않는다. 반환 행 0건도 성공이 아니다.
  서버 스키마/데이터에 대한 마이그레이션, 운영 데이터 읽기/쓰기, 운영 배포는 실행하지 않았다.

## 자동 검증 결과

`npm test` (Node v24.22.1): **23개 통과, 실패 0개**.

검증 대상: 성공 확인, SDK 오류/누락 응답, 저장 실패, 오프라인 복구, 미저장 입력 보호,
읽기 전용 기기의 갱신, 동시 저장 CAS 충돌, 저장 중 추가 입력, 최초 조회 중 입력,
최초 조회 실패, 새로고침 복구, 응답만 유실된 저장의 재확인, 충돌 해소 및 재충돌,
백업 용량 초과, 기존 로컬/서버 불일치, 빈 서버 초기 시드, 종료 후 늦은 응답,
중복 요청 방지, 손상된 대기 기록, StrictMode 재마운트 및 SDK 호출 조건.

상태 머신과 SDK 호출 경계는 모의 서버/SDK로 검증했다. 실제 브라우저에서 React 훅을
마운트한 통합 테스트나 운영 DB의 조건부 UPDATE를 실행한 결과는 아니다.

`git diff --check`: 통과.

`npm ci`: 실행 환경의 패키지 다운로드 403 및 오프라인 캐시 누락으로 실패.
따라서 `npm run build`, `npm run lint`는 도구 미설치로 완료하지 못했다.
이 실패를 코드 빌드/린트 통과로 표시하지 않는다. 의존성/lockfile 버전은 변경하지 않았다.
GitHub Actions에는 의존성이 필요 없는 회귀 테스트와 별도 빌드/린트 작업을 추가했다.

## PC·모바일 및 스테이징 추가 검증

운영 기록 대신 별도 InsForge 테스트 프로젝트/복제 테이블과 가상 참가자를 사용한다.
테스트 프로젝트의 URL/공개 클라이언트 키는 기존 `VITE_INSFORGE_URL`,
`VITE_INSFORGE_ANON_KEY` 환경변수로 설정하고 `npm ci`, `npm run dev`를 실행한다.
운영 키나 실제 경기 기록을 테스트에 사용하지 않는다.

| 확인 항목 | 합격 조건 |
|---|---|
| DB 스키마·권한 | JSON 필드가 등가 비교 가능한 jsonb인지 확인. anon/auth 사용자의 SELECT/UPDATE 및 반환 행 확인 권한 검증 |
| SDK·서버 호환성 | 8개 WHERE 조건이 서버에서 하나의 원자적 UPDATE에 적용되는지, null/JSON/배열 값이 정확히 비교되는지 검증 |
| 정상 저장 | PC 입력 후 저장 완료 표시, 모바일에 같은 참가자·대진표·점수 표시 |
| 오프라인 | 모바일 비행기 모드에서 점수 입력 후 대기/오류 표시. 5초 이상 지나도 입력 유지 |
| 복구·재시작 | 오프라인 입력 후 새로고침/앱 재실행, 대기 기록 유지. 연결 복구 후 저장 또는 충돌 표시 |
| 동시 수정 | 두 기기가 같은 기준에서 수정하면 한쪽 저장, 다른 쪽 충돌. 다른 코트 수정도 단일 행 충돌로 처리 |
| 응답 유실 | 서버 반영 후 응답만 차단해도 읽기 재확인으로 완료 처리. 추가 입력이 있으면 보존 |
| 충돌 선택 | 양쪽 내용 비교·JSON 내려받기·취소·서버 적용·내 기록 저장을 각각 확인 |
| 저장 용량/사생활 모드 | localStorage 실패 경고, 백업 불가 시 충돌 해소 중단, JSON 다운로드 확인 |
| 모바일 수명주기 | Safari 백그라운드/화면 잠금/앱 종료 후 복귀 시 기록과 상태 표시 확인 |
| 큰 대진표 | 최대 예상 대진표 크기로 조건부 UPDATE URL 길이 제한과 요청 제한 시간 확인 |
| 기존 경기 기능 | 동일 참가자/설정으로 대진표 규칙 유지, 듀스·타이브레이크·완료·통계 계산 확인 |

## 잔여 위험과 적용 조건

- **모든 쓰기 기기를 새 버전으로 전환해야 한다.** 기존 버전의 무조건 UPDATE나 별도
  외부 쓰기 도구까지 클라이언트 CAS만으로 통제할 수 없다. 경기 시작 전 모든 탭을 새로고침한다.
- 단일 행 전체 비교이므로 서로 다른 코트의 수정도 충돌할 수 있다. 점수/대진표의
  연관성을 보존하기 위해 자동 병합하지 않았다. 동시 입력량이 많아지면 경기별 행과
  서버 측 revision 기반 RPC로 분리하는 후속 설계가 필요하다.
- JSON이 json 타입이거나 서버가 필터를 지원하지 않으면 저장은 오류 상태로 남는다.
  안전하지 않은 무조건 UPDATE로 우회하지 않는다. 운영 반영 전에 스테이징에서 확인한다.
- 데이터 전체 비교는 버전 번호 방식과 달리 A→B→A의 중간 변경 이력을 감지하지 못한다.
  이 변경은 감사 이력/완전한 경기별 병합 시스템을 제공하지 않는다.
- 브라우저 저장소 삭제, 다른 탭에서 동일 키 수정, 운영체제 강제 종료까지 영구 보관을
  보장하지 않는다. 미저장 표시가 남으면 창을 닫기 전에 JSON 백업을 내려받는다.
- 경기 이력 테이블과 Google Sheets 전송은 별도 기존 경로로, 이번 공유 상태 동기화의
  원자적 저장 범위에 포함되지 않는다.

SDK 방식 확인 자료: InsForge 공식 SDK의 `src/modules/database-postgrest.ts` 및
`SDK-REFERENCE.md` (https://github.com/InsForge/InsForge-sdk-js).
